## 1. 왜 운영까지 해봐야 하는가

### 소스 분석이 놓치는 것들

compare_claws 저장소는 현재까지 14개 프레임워크의 **소스 구조 + 문서 + 설계 원리**를 체계화했다. 그러나 아래 질문들은 **실제로 한 번 돌려봐야** 답이 나온다:

| 질문 유형 | 예시 |
|----------|------|
| **암묵적 UX** | 에러 메시지가 친절한가? 첫 배포까지 걸린 시간은? |
| **실제 성능** | LLM API 왕복 시간 외에 프레임워크 오버헤드가 얼마나 되나? |
| **실패 모드** | HN 다운/LLM rate-limit/디스크 풀 상황에서 어떻게 망가지나? |
| **커뮤니티 응답** | Discord/GitHub 이슈에 얼마나 빠르게 답이 오나? |
| **비용 실측** | 문서에 적힌 "$5/day" 가정이 실제로 맞나? |
| **데몬 안정성** | 24시간 연속 운전 시 메모리 누수, crash loop, 재시작 복원력은? |

소스 분석은 "설계 의도"를 읽고, 운영은 "현실 마찰"을 측정한다. 둘은 보완적이다.

### 학습 곡선 데이터의 가치

운영 경험은 이후 **의사결정의 근거**가 된다:
- 팀/고객에게 "X를 골라야 한다"고 말할 때 소스 분석보다 운영 데이터가 설득력 있음
- 밋업 발표 / 블로그 시리즈 / 오픈소스 기여(이슈·PR)의 소재
- 사용자의 본 시스템(Hermes standalone) 결정에 대한 **사후 검증**

## 2. 프레임워크별 "운영해야만 보이는 것"

선행 리포트가 구조적 특징은 충분히 기록했으므로, 이 표는 **운영 전용 관찰 항목**만 선별:

| # | 프레임워크 | 운영 관찰 포인트 | 우선순위 |
|---|-----------|------------------|---------|
| 1 | **OpenClaw** | 12+ 채널 동시 운영 로드, ACP/Tailscale 멀티 노드 실전(Gateway-Node R32 진짜 동작하는지), SecretRef 64-surface UX, Docker 샌드박스 부팅 지연 | ⭐⭐⭐ (생태계 중심) |
| 2 | **Hermes Agent** | Tirith 실제 false positive 비율 (정상 도구 오탐?), Skills Trust 4단계 UX 마찰(커뮤니티 스킬 설치 흐름), session_db 축적 속도, Frozen Snapshot prefix cache 실제 비용 절감 % | ⭐⭐⭐ (사용자 결정 검증) |
| 3 | **IronClaw** | WASM 샌드박스 퍼포먼스 오버헤드 (네이티브 대비 %), Zero-Exposure 자격증명 프록시 실사용감, 커뮤니티 도구 WASM 포팅 현실성 | ⭐⭐ (보안 관심 시) |
| 4 | **GoClaw** | Go 단일 바이너리 배포 매끄러움 (scp만으로 끝나나?), Tailscale tsnet VPN-native 운영 편의, Docker 3축 샌드박스 프로필 조합의 실용 범위 | ⭐⭐ (배포 단순성 관심) |
| 5 | **CoPaw** | 14채널 동시 처리 시 R42 UnifiedQueueManager 실동작 (head-of-line blocking 정말 사라지나), browser_control 3,460L 안정성, skill_scanner false positive | ⭐⭐ (다채널 관심) |
| 6 | **MetaClaw** | Swap-Runtime Proxy 실제 백엔드 교체 1-줄 명령의 깔끔함, MadMax 유휴-창 훈련이 실제로 체감 제로인지, GEPA 훈련 $2–10 주장 실측 | ⭐⭐ (자기 개선 관심) |

**제외된 것**:
- Claude Code, NemoClaw, NullClaw, Paperclip, OpenJarvis, OpenFang, Nanobot, NanoClaw, ZeroClaw, PicoClaw, TinyClaw — 각자 이유 있지만 초기 6개에선 제외 (Hermes 우선 검증이 사용자 시스템 결정에 직결되고, OpenClaw·IronClaw·GoClaw·CoPaw·MetaClaw가 나머지 4개 축(멀티 디바이스/보안/배포/다채널/자기개선)의 대표이기 때문)
- 나머지 10개는 **Phase 2**에서 선택적 추가

## 3. 현실적 함정 2가지

### 3.1 시간 비용

현실적 시간 추정:

| 단위 | 세부 작업 | 시간 |
|------|----------|------|
| 설치 + 기본 설정 | OCI 인스턴스 프로비저닝, 의존성, Telegram 토큰 연동 | 2–4h |
| 벤치마크 태스크 구현 | 스킬·프롬프트·Cron 스케줄 | 3–6h |
| 3–5일 운영 관찰 | 수동 일지 기록, 실패 모드 트리거 시도 | 5–10h (대기 시간 제외) |
| 정리 + 비교 노트 | 마크다운 기록 | 1–2h |
| **프레임워크당 소계** | | **11–22h** |

**6개 프레임워크 총합**: 66–132시간

- **주말 취미 (8h/주)**: 8–16주 = **2–4개월**
- **평일 2h/일 + 주말 (18h/주)**: 4–8주 = **1–2개월**
- **풀타임 집중 (40h/주)**: 2–4주

### 3.2 비교 가능성 상실

각 프레임워크를 다른 태스크로 돌리면 배운 게 축적 안 됨:
- "OpenClaw로 블로그 자동화 만들어봄" + "Hermes로 논문 요약 만들어봄" → **동일 축 비교 불가**
- 공평한 비교를 위해선 **입력·출력·SLO가 동일**해야 함

**해결책**: 고정된 벤치마크 태스크 하나 정해서 6개 모두 동일하게 돌리기.

## 4. 공통 벤치마크 태스크 설계

### 4.1 태스크 정의 — 3-Tier 구조

**T1 (Minimum)**: 모든 프레임워크가 반드시 통과해야 하는 기본 기능
```
매일 09:00 KST, Hacker News 상위 10개 기사를 fetch → 한국어 3줄 요약 →
Telegram @me 봇 채널로 전송. 이미 전송한 기사는 중복 제외.
```

**T2 (Standard)**: 스킬·메모리·상태 관리 검증
```
T1 + 요약 스타일을 skill/SKILL.md로 분리 (예: "기술 중심 vs 비즈니스 중심").
전송 후 내가 "more on #3"이라 답하면 해당 기사의 전체 본문을 fetch해
심층 요약을 회신. 3일치 요약 히스토리를 프레임워크 메모리에 유지.
```

**T3 (Stretch)**: 멀티-에이전트·HITL·자기개선 검증
```
T2 + "experiment"라고 답하면 Research Agent 스폰해 해당 기사에서
언급된 모델/도구(예: glm-ocr)를 pip/npm으로 설치·비교 벤치마크 실행 →
결과를 Telegram 회신. 3개월 후 축적된 session_db에서 자기 개선(스킬
자동 진화 or config 튜닝) 1회 시도.
```

### 4.2 태스크 선정 이유

T1 혼자서도 이미 핵심 축들을 커버:
- **Cron/스케줄러** 작동 여부
- **Telegram outbound** (에이전트가 먼저 말 거는 패턴)
- **상태 관리** (중복 감지)
- **LLM 도구 호출** (fetch + summarize)
- **24h 데몬 안정성**

T2/T3는 Hermes·MetaClaw 등 기능 풍부한 프레임워크에서만 구현 시도. **IronClaw/ZeroClaw/TinyClaw 같은 경량은 T1에서 멈춤**.

### 4.3 입력·출력 고정

| 요소 | 값 |
|------|-----|
| **입력 소스** | `https://news.ycombinator.com/` (front page 스크랩) + `https://hn.algolia.com/api/v1/search?tags=front_page` (API) 선택 |
| **요약 LLM** | Claude Sonnet 4.6 (`claude-sonnet-4-6`) 고정. 프레임워크가 자체 프로바이더 지원 시 Anthropic API 직접 호출 |
| **출력 채널** | Telegram (BotFather 단일 봇, 프레임워크마다 다른 chat_id 허용) |
| **타임존** | Asia/Seoul (KST) 고정 |
| **중복 판정** | HN story ID 기준 |

### 4.4 SLO (Service Level Objectives)

운영 안정성 기준:

| 지표 | 목표 |
|------|------|
| **일일 발송 성공률** | ≥ 95% (30일 기준) |
| **발송 시각 정확도** | 09:00 ± 5분 |
| **중복 전송** | 0건 |
| **24h 연속 운전** | 사람 개입 없이 3일 이상 |
| **복구 시간 (crash 후)** | < 5분 (자동 재시작) |

## 7. 일정 옵션 3가지

### Option A — 본 시스템 구축 완료 후 (순차)
- 2026-04-14 ~ 2026-05-31 (~6주): Hermes standalone 본 시스템 구축, 안정 운영
- 2026-06-01 ~ 2026-07-31 (~8주): 프레임워크 6개 벤치마크 (1개당 1–2주)
- 장점: 본 시스템 우선, 방해 없음
- 단점: 벤치마크 경험이 본 시스템 결정을 역전시킬 기회 놓침

### Option B — 본 시스템과 병행 (평일 본, 주말 벤치마크)
- 본 시스템 구축하면서 주말마다 다른 프레임워크 1개 설치·3일 운영
- 약 6–10주 병행
- 장점: 조기 피드백, 다른 프레임워크의 아이디어를 본 시스템에 역수입 가능
- 단점: 분산된 주의, 각각의 깊이 얕음

### Option C — Hermes 먼저 검증 (pre-build)
- 2–3주 Hermes 단독 벤치마크 (사용자 결정 검증 겸용)
- 만족 시 본 시스템 구축 진행, 만족 못 하면 재평가
- 나머지 5개는 이후 선택적 진행
- 장점: 결정 위험 최소화, 본 시스템 자신감 획득
- 단점: Hermes가 의외로 안 맞을 때 다시 원점

**추천**: **Option C** (pre-build 검증) → 본 시스템 구축 → 여유 시간에 나머지 5개.
